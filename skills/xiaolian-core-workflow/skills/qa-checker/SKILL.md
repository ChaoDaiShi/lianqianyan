# QA Checker（质量检查 / 最终防线）

## 能力契约

| 字段 | 内容 |
|------|------|
| 职责 | 所有最终输出的静默质量检查与自动修正 |
| 适用场景 | 所有最终输出（回复、文件、成果） |
| 不适用场景 | 中间推理过程、内部讨论 |
| 必要输入 | 待输出的回复内容 |
| 标准输出 | 检查并修正后的最终回复 |
| 完成条件 | 6 项检查全部通过 |
| 失败回退 | 无法确认的项标记而非删除 |
| 可组合 | 所有 Skill（作为最后一道闸门） |

## 定位

这是一个**静默执行**的元技能。在每次向用户输出最终回答之前，自动运行本检查。用户看不到检查过程，只收到检查并修正后的最终结果。

## 检查清单（静默执行）

### 1. 回答是否回答了原问题？
- 逐字对照用户的问题，确认每个子问题都得到了回应
- 如果用户问了 A，你回答了 B，立即补充 A 的回答
- 如果问题隐含了多个子问题，确认每个都有答案

### 2. 是否遗漏了明确的要求？
- 用户指定的格式（"用表格"、"分三步"、"不超过 200 字"）
- 用户指定的范围（"只看 foo.js"、"只关心性能"）
- 用户指定的输出方式（"直接给代码"、"不要解释"）

### 3. 是否存在事实错误？
- 凡是用你知识库回答的内容，快速自检：有没有把握？
- 不确定 → 标记为"不确定"而非断言
- 代码中的 API 名称、参数顺序、返回值类型是否准确

### 4. 格式是否一致？
- 同一回答中同一概念的名词一致
- 列表格式统一（全是完整句 or 全是关键词）
- 代码块标注了语言
- 中英文混排格式统一

### 5. 是否存在明显矛盾？
- 回答的前后部分是否互相矛盾
- 结论和建议是否一致

### 6. 是否还有一步可以顺手完成？
- 如果用户问"这个 bug 怎么修"，除了指出来，你能否直接修好？
- 如果用户问"这是什么意思"，除了解释，你能否给一个例子？
- 如果能顺手多走一步而显著提升价值，直接做了

## 修正规则

- 发现问题 → 直接修正后输出，不告诉用户"我发现了 X 问题并已修正"
- 需要补充 → 直接补充
- 格式问题 → 直接调整
- 只有一种情况需要告知用户：你发现自己之前在这轮对话中的前一条回答有错误，需要纠正——此时仅说"上一条有误，纠正如下"

## 执行时机

**在每次向用户输出最终回复之前**，静默过一遍本清单。不增加额外 token 输出给用户，不展示"已通过 QA 检查"之类的确认信息。
